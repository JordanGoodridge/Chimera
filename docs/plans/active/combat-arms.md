# Combat Arms on Chimera

Started 2026-10-18. Re-implementing Combat Arms (the Classic, LithTech
Jupiter) as a game library on Chimera, `games/combat_arms`, from specs.
Replaces the local-only "MVP: Combat Arms slice" plan (2026-10-03), whose
still-relevant steps and decisions are folded in below.

Goal of the first slice (unchanged from the MVP): start a match on one map,
run, sprint, shoot and fight bots with Combat Arms movement and weapons,
built through the slots so another game's movement or weapons swap in by
loadout. Verified by scenario tests from each spec's test cases, then side
by side against the real game.

## Rules (the user's decisions, 2026-10-18)

- **Public repo, faithful recreation.** The goal is a
  faithful recreation of the game, built without distributing anything we
  don't own: no game assets, extracted files, keys or third-party code in
  the repo; players load assets from their own install. Spec sessions on
  the user's Windows PC work from reference material the user points them
  to and write `specs/combat_arms/*.md` in our own words; implementation
  sessions (the Linux box, cloud agents) read specs only (specs/README.md).
  Specs go to main like any other spec, after the user's review.
- **Keys** (V1/V2 resource keys) only in the git-ignored `chimera.local.toml`.
  **No assets** in git, extracted or converted.
- **Default data is ours.** Spec numbers go into our own data files
  (`games/combat_arms/data/weapons/*.toml`, like
  `games/cs_source/data/weapons/*.toml`; docs/weapon-data.md). When keys are
  present, the install's real attribute data overrides them at run time
  (item 3's spec says how to read it).
- **Cloud agents have no assets.** Placeholder visuals (capsules, box guns),
  tiny fixture files generated by the tests for format readers. Heavy tests
  that need the real install run on the Linux box (pre-push, `heavy::`,
  skipping when the install isn't there).

## Workflow

1. The user runs many spec sessions on the Windows PC in parallel, one spec
   file each (briefs below), each pushed straight to main.
2. The coordinator watches main for landed specs and assigns **one
   implementation agent per landed spec**: a cloud agent for asset-free
   logic (movement, firing, inventory, HUD; tested by scenario tests built
   from the spec's numbered test cases), this box for readers and rendering
   that need the real install.
3. No duplicate work: one owner per item on the board below (the owner's
   branch goes in the status), and the skeleton keeps each subsystem in its
   own module so parallel agents touch different files. Shared code is the
   exception: see "Sharing with CS:S".
4. Open questions in a spec go back to a short follow-up spec session; the
   implementer records the answer it assumed in the code's `//!` doc and in
   the spec's "Open questions" via the coordinator, never by guessing
   silently.

Status values: not started / spec in progress / spec landed /
implementing (owner branch) / done.

## Sharing with CS:S

When a Combat Arms item needs something `games/cs_source` already has
(inventory and switching, HUD widgets, view-model and player animation,
rounds and teams, spectating, bots, impact effects, ...), the implementing
agent first **lifts** it into Chimera: generic, with the game supplying data
and hooks, CS:S's behaviour unchanged and its tests passing. Then
`games/combat_arms` uses it from Chimera.

- Never copy CS:S code into `games/combat_arms`, and never depend game on
  game (`checks/tests/it/architecture.rs` refuses it).
- Lift at the point of second use, not ahead: the CA spec shows what
  actually differs.
- Lifts touch shared code, so only one lift per area at a time. The board's
  "Lift" column names the likely one (by its `L` number in "Lift survey
  (Wave 0.5)" below); the owner of an item writes "lifting (branch)" there
  while doing it, and others in the same area wait.

## LithTech loader layer

Combat Arms' file formats (`.rez` archives, the world `.dat`, models
`.ltb`, textures `.dtx`, and whatever else LithTech Jupiter reads) go in a
new **`lithtech/`** loader layer beside `source/`, not in Chimera and not in
`games/combat_arms`: like `source/formats` (`source_formats`), a plain-data
crate that turns bytes into Rust values with no Bevy (say
`lithtech/formats`, `lithtech_formats`), and, if LithTech map logic or
conversion into engine types ever needs Bevy, a second crate beside it
(as `source/logic` is). `games/combat_arms` converts what it reads into
Chimera's neutral types (`MapData`, `AnimSet`, textures), as `cs_source`
does for BSP.

- Done 2026-10-18: the first crate is `lithtech/formats`
  (`lithtech_formats`): the `.rez` reader, moved from the old local-only
  code and checked against `rez_archive.md` (`rez`: header, directory,
  archive as a mount layer, `open_dir` for a folder; `rez_cipher`: the
  payload cipher, keys at run time). Unit tests on archives written in
  code; `heavy::` tests on this box's install. It uses `source_formats`
  only for the VFS (`fs::FileSource`, `Mount`).
- `games/combat_arms`' `game::mount` (its `INFO.open`) mounts the
  install's `Game/` with `rez::open_dir` and the keys from
  `chimera.local.toml`; the data seam (`game/data.rs`) reads the
  install's `ATTRIBUTES.rez` with the same keys.
- 2026-10-18: `lithtech_formats::world` reads world files (`.dat`) and
  `lithtech_formats::dtx` textures; `games/combat_arms`' `game::world`
  turns a map into `MapData` (`--map combat_arms:<name>`).
- 2026-10-18: `lithtech_formats::attributes` reads attribute files
  (`attribute_data.md`'s format); Combat Arms' records and the merge
  over our TOML are the game's (`game/data.rs`, `game/data/attributes.rs`).
- 2026-10-18: `lithtech_formats::ltb` reads models and `anim` their
  animation data and playback rules; `games/combat_arms`' `game::model`
  turns a model into a skinned `MapModel` with Chimera's `AnimSet`.
- LithTech behaviour that every game could use (as with CS:S pieces) is
  lifted into Chimera, not kept in `lithtech/`; `lithtech/` holds only what
  is about LithTech's files and conventions.
- docs/ARCHITECTURE.md ("Crates") and `checks/tests/it/architecture.rs`
  know `lithtech/`: `workspace_crates` holds `lithtech/formats` to the
  rules `source_formats` has (no Bevy, avian, Chimera or game; no
  workspace-hack), and `no_keys_tracked` refuses key-like hex runs in
  `lithtech/` and Combat Arms' code and specs.
